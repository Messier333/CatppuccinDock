# 로그인·SSO·보안

[프로젝트 소개·실행](../README.md)

## 로그인 기기 관리

**설정 → 계정 · 보안 → 로그인 기기 관리**에서 현재 기기와 다른 브라우저의 유효 로그인을 확인합니다. 관리자와 일반 사용자 모두 본인 기기만 조회·종료할 수 있습니다. 브라우저·운영체제·최근 접속 IP·로그인/최근 활동/만료 시각을 표시하며 다른 기기는 5개씩 나눠 봅니다. 기기 정보는 브라우저가 보내는 User-Agent를 바탕으로 표시합니다.

기기별 **로그아웃**은 해당 세션을 폐기합니다. **다른 기기 모두 로그아웃**은 현재 기기를 유지하고 나머지 세션과 대기 중인 2FA 로그인을 종료합니다. 종료된 세션은 다음 API 요청부터 거부됩니다. SSO 인증 서비스 자체의 로그인은 유지되므로 해당 서비스의 기기 관리와는 별개입니다.

최근 활동과 접속 IP는 인증된 요청에서 최대 1분에 한 번 DB에 기록하며 세션의 기존 7일 만료 시간을 연장하지 않습니다. 목록은 화면이 보일 때 1분 간격으로 새로고침하며 직접 새로고침할 수도 있습니다. 기기 관리용 공개 UUID는 인증 토큰이나 토큰 해시와 별개입니다. 업데이트 시 기존 세션·쿠키·만료 시간을 보존하며 이전 로그인은 다음 활동 기록 전까지 기기/IP 정보가 없을 수 있습니다. 비밀번호·2FA 설정 변경으로 현재 세션이 교체되면 목록도 새 세션으로 갱신합니다.

## 2단계 인증

**설정 → 계정·보안 → 인증 앱 연결**에서 현재 비밀번호를 확인하고 QR 코드를 스캔합니다. 인증 앱에 표시되는 6자리 코드로 등록을 완료하면 일회용 복구 코드 10개를 발급합니다. 복구 코드는 최초 발급 화면에서 파일로 보관하세요.

로그인 시 비밀번호 확인만으로는 포털 세션이 발급되지 않습니다. 5분 안에 인증 코드 또는 미사용 복구 코드로 추가 인증해야 합니다. 사용한 TOTP와 복구 코드의 재사용, 만료된 인증 요청, 반복된 추측 요청을 거부합니다. 2FA 비밀키는 암호화하고 복구 코드·로그인 세션 토큰은 해시로만 DB에 보관합니다.

SSO 전용 계정은 최근 10분 이내의 SSO 로그인 후 인증 앱을 등록할 수 있습니다. 로컬 2FA가 설정된 계정은 SSO 로그인 뒤에도 로컬 2FA를 확인합니다. 포털 로그아웃은 포털 세션을 종료하며, 인증 서비스 자체의 세션은 해당 서비스에서 종료합니다.

서버 운영자 복구 명령:

```bash
docker compose exec backend python -m app.cli reset-password 사용자아이디
docker compose exec backend python -m app.cli reset-2fa 사용자아이디
```

비밀번호는 화면에 표시하지 않고 입력받습니다. 사용자아이디를 생략하면 첫 관리자 계정을 대상으로 합니다. 복구 시 해당 계정의 세션을 폐기합니다.

## SSO · OpenID Connect

Authentik·Keycloak 등의 **Authorization Code + PKCE(S256)** 흐름을 지원합니다. **관리자 → 계정 · 보안 → SSO · 로그인**에서 Issuer URL, Client ID, Client Secret, Callback URL을 등록하고 SSO 로그인을 활성화하세요. 저장 즉시 적용되며 컨테이너 재시작이 필요하지 않습니다. Client Secret은 `AUTH_ENCRYPTION_KEY`로 암호화하여 DB에 저장하고 화면/API로 반환하지 않습니다. Secret 입력을 비워두면 기존 값을 유지합니다.

**로그인 허용 방식**에서 다음 중 선택합니다.

- **아이디·비밀번호만**: 비밀번호 입력창을 표시하고 SSO 로그인을 비활성화합니다.
- **아이디·비밀번호 + SSO**: 비밀번호 입력창과 설정한 이름의 SSO 버튼을 함께 표시합니다.
- **SSO만**: SSO 버튼만 표시하며 비밀번호 로그인 API도 차단합니다. 먼저 **사용자 관리 → 관리자 계정 → SSO 연결**에서 현재 Issuer의 관리자 Subject를 연결하세요. 활성 관리자의 해당 SSO 연결이 없으면 저장할 수 없습니다.

SSO 전용 모드에서도 해당 계정의 포털 2FA는 유지됩니다. 이미 로그인한 세션은 유지하며, 전용 모드 전환 전에 시작한 비밀번호 2FA 요청은 폐기합니다. 마지막 SSO 관리자의 연결 해제·비활성화·권한 변경 또는 연결되지 않은 Issuer로의 변경은 막습니다. 이전 설정에는 비밀번호 로그인을 허용하는 기본값을 적용합니다.

인증 서비스 장애 시 서버 운영자가 비밀번호 로그인을 다시 허용할 수 있습니다. 로그인 화면에는 우회 경로를 제공하지 않습니다.

```bash
docker compose exec backend python -m app.cli enable-password-login
# 관리자에게 비밀번호가 없는 경우 함께 실행
docker compose exec backend python -m app.cli reset-password 사용자아이디
```

Callback URL은 외부에서 접속하는 주소에 `/api/auth/oidc/callback`을 붙인 값입니다. 예: `https://dock.example.com/api/auth/oidc/callback`. 경로 프록시를 사용하면 `/proxy/8090/` 등 실제 경로를 포함하세요. 인증 서비스에도 동일한 Redirect URI를 등록해야 합니다. Issuer는 discovery 응답의 값과 정확히 일치해야 합니다.

**사용자 관리 → 사용자 추가 → 로그인 방식**에서 일반 계정 또는 OIDC 계정을 선택합니다. OIDC 계정은 등록한 인증 서비스의 사용자 고유 `sub` 값(Subject)을 입력합니다. 이 작업은 인증 서비스에 사용자를 생성하는 것이 아니라 기존 인증 서비스 사용자에게 포털 접근 권한을 부여합니다. 기존 일반 계정에 SSO 연결을 추가할 수도 있습니다. 관리자 등록 없이 첫 SSO 로그인으로 계정을 자동 생성하지 않습니다. 이메일·동일한 아이디만으로 자동 연결하지 않습니다.

설정 변경 시 진행 중인 OIDC 인증은 다시 시작해야 합니다. 변경 후 허용되는 로그인 방식으로 접근 가능한 관리자가 최소 한 명 있어야 합니다. 기존 환경변수 설정은 DB에 OIDC 설정이 없는 최초 실행 시에만 읽는 이전 경로로 남아 있으며 이후 DB 설정을 사용합니다. 현재 Compose에는 OIDC 환경변수를 지정할 필요가 없습니다.

## 로그인 실패 로그와 fail2ban

앱의 IP별 반복 시도 제한과 fail2ban의 방화벽 차단은 별개의 기능입니다. Compose는 일반 로그인·2FA·최초 설정 실패(401/403/422/429)를 `logs/auth/auth.log`와 백엔드 표준 로그에 기록합니다. 로그에는 IP·인증 단계·상태 코드만 남기며 아이디·비밀번호·인증 코드를 기록하지 않습니다. 일반 페이지의 401/403이나 정상 로그인은 실패 이벤트로 집계하지 않습니다. SSO 서비스 자체의 로그인 실패는 인증 서비스에서 기록·차단해야 합니다.

fail2ban이 자동 설치되거나 jail이 자동 활성화되는 것은 아닙니다. 아래 파일은 연동을 준비한 설정이며 실제 fail2ban 호스트에서 설치·활성화해야 IP 차단이 동작합니다.

- 필터: `deploy/fail2ban/filter.d/catppuccindock.conf`
- jail 예시: `deploy/fail2ban/catppuccindock.local.example` (15분 동안 5회 실패, 1시간 차단)
- 실제 로그 경로: `<프로젝트 경로>/logs/auth/auth.log`

Docker 호스트의 실제 방화벽 구조·로그 경로에 맞게 jail을 설정해야 합니다. 예시는 `DOCKER-USER`와 `iptables-allports`를 사용하므로 해당 체인이 존재하는지 확인하세요. 다른 서버의 리버스 프록시에서 차단하는 경우 그 서버에 로그를 전달하고 해당 서버의 차단 액션을 사용해야 합니다.

리버스 프록시 뒤에 두면 프록시 IP가 사용자 IP 대신 기록될 수 있습니다. `deploy/nginx/trusted-proxies/proxy.conf.example`의 주소를 실제 프록시 IP로 바꿔 `.conf` 파일로 저장한 뒤 프런트를 재시작하세요. 신뢰할 프록시만 지정하고 모든 주소를 신뢰하지 마세요. 프록시도 올바른 `X-Forwarded-For`를 덮어쓰거나 추가해야 합니다. 직접 8090으로 접속하면 nginx가 접속 IP로 `X-Real-IP`를 덮어쓰며, 외부에서 전달한 임의 `X-Real-IP`는 그대로 신뢰하지 않습니다. IP가 정확히 기록되고 실제 차단 후 접속이 막히는지 별도로 검증해야 연동 완료로 볼 수 있습니다.

```bash
fail2ban-regex logs/auth/auth.log deploy/fail2ban/filter.d/catppuccindock.conf
```
